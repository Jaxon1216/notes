# 写作规范

本文用于约束仓库里的 Markdown/MDX 内容，重点覆盖 `content/docs/` 下的公开文章。目标是让多人提交 PR 时保持目录清晰、标题层级稳定、Fumadocs 渲染一致。

## 文件位置

新增笔记时放到最接近主题的目录：

- 知识八股：`content/docs/<direction>/knowledge/`
- 面经：`content/docs/<direction>/interview/`
- 优质文章和项目：`content/docs/<direction>/resources/`
- Agent 应用工程：`content/docs/agent/knowledge/agent/`
- LLM 原理：`content/docs/agent/knowledge/llm/`
- 算法基础和刷题复盘：`content/docs/algorithm/basics/` 或 `content/docs/algorithm/leetcode/`
- 零散技巧、读书笔记和未归档资料：`content/docs/dev/notes/`

目录名优先使用英文。页面展示名放在 `meta.json` 或文章标题里维护。

## 文件命名

- 文件名使用清晰标题，可以用数字前缀控制排序，例如 `01-核心概念.md`。
- 连续课程型专题使用数字前缀，例如 `00-总览.md`、`01-启动与入口.md`、`02-请求解析.md`。适用于需要按固定顺序阅读的源码解析、框架原理、学习路径类内容。
- 独立主题集合不强制使用数字前缀，例如 `stl.md`、`algorithm.md`、`cpp-constructors-overload.md`。适用于每篇文章可以单独搜索和单独阅读的知识点集合。
- 同一目录内尽量保持一种命名方式。不要无说明地混用“部分有数字前缀、部分无数字前缀”；如果目录实际是混合型，优先拆成多个更小专题目录。
- 混合型目录暂时不拆时，按主要阅读方式选择统一命名：偏学习路径就全部补数字前缀，偏主题集合就去掉数字前缀，并在 `meta.json` 的 `pages` 中维护展示顺序。
- 图片放到当前专题附近的 `img/` 目录，并使用相对路径引用。
- 不提交构建产物、临时文件、截图草稿和个人编辑器状态。

## 目录元信息

Fumadocs 使用 `meta.json` 维护目录元信息。它不应该成为每篇文章的重复索引，只在目录展示确实需要时使用。

- 一级方向、二级栏目和专题目录需要中文展示名时，保留 `meta.json` 的 `title`。
- 目录需要说明定位时，可以补充 `description`。
- `pages` 只用于手动排序、分组或隐藏页面。文件名已经用 `00-`、`01-` 等前缀表达顺序时，不要重复维护完整 `pages` 列表。
- 叶子专题目录的 `meta.json` 尽量只保留必要字段，例如只写 `title`。

## Markdown 与 MDX

普通内容默认使用 `.md`。多人维护时，优先保证文章可以被通用 Markdown 编辑器、预览器和格式化工具稳定处理。

- 新增普通文章、面试题、学习笔记和项目复盘时，使用 `.md`。
- 只有需要 JSX、React 组件、组件 `import`、交互 Demo 或 Fumadocs 专属 MDX 组件时，才使用 `.mdx`。
- `.mdx` 文件仍需遵守 Markdown 标题层级、图片引用和代码块语言标注规则。

## 图片资源

图片资源默认采用“专题就近存放”规则，避免多人维护时出现跨目录引用和迁移断链。

- 图片放在当前文章所在专题目录的 `img/` 子目录下，例如 `content/docs/frontend/knowledge/ajax-promise-axios/img/event-loop.png`。
- 文章中使用相对路径引用当前专题图片，例如 `![事件循环流程](./img/event-loop.png)`。
- 不要使用 `../img/`、`../../img/` 跨专题引用图片。确实被多个专题复用的图片，应优先复制到各专题 `img/`，或在上层专题建立明确的共享资源目录并在文档中说明。
- 图片文件名使用英文小写、数字和短横线，例如 `event-loop.png`、`request-flow.svg`。
- Markdown 图片必须填写有意义的 alt 文案，不要写空的 `![](...)`。
- 不建议直接引用远程图片。确需保留远程图片时，应确认来源稳定，并填写 alt 文案。

## 标题层级

推荐结构：

```markdown
# 文章标题

## 一级正文章节

### 二级正文小节

#### 细节说明
```

约束规则：

- 普通文章推荐使用一个 `#` 作为文章标题。
- 同一篇文章最多只能有一个 `#`。
- 如果文章已经用 frontmatter `title` 或文件名作为页面标题，正文可以直接从 `##` 开始。
- `##` 表示正文主章节，`###` 表示章节内的小节，`####` 表示更细的解释。
- 标题必须逐级下降，不能从 `##` 直接跳到 `####`。
- 标题中不要直接写 Markdown 链接，链接放到标题下面的正文里。
- 问答型长文使用 `## 题目`、`### 回答重点`、`### 扩展知识`、`### 面试官追问`。
- 指向其他 Markdown/MDX 页面的相对路径需要写成 Markdown 链接，例如 `[LLM 原理](../llm/LLM原理.md)`；不要只写成 `` `../llm/LLM原理.md` ``，否则前端会渲染为不可点击的代码文本。

这样做的原因是 Fumadocs 会根据标题生成目录和锚点。多个 H1、标题跳级、标题里嵌套链接都容易导致右侧目录和锚点渲染不稳定。

## Frontmatter

普通文章可以不写 frontmatter，页面标题会从文件名或正文 H1 推导。需要覆盖展示标题或描述时再写：

```md
---
title: 自定义标题
description: 页面描述
---
```

不要为了排序在 frontmatter 里维护重复信息。排序优先使用文件名前缀和 `meta.json`。

## 内容结构

知识型文章建议按这个顺序组织：

```markdown
# 主题名称

## 核心结论

## 背景和概念

## 代码示例

## 常见误区

## 扩展阅读
```

面试题文章建议按这个顺序组织：

```markdown
# 主题名称

## 题目

### 回答重点

### 扩展知识

### 面试官追问
```

项目推荐文章必须包含：

- 原文或项目链接
- 推荐理由
- 标签

## 讲解型技术文章写法

面向初学者、跨语言迁移或八股知识补全的文章，优先写成「能读懂、能验证、能迁移」的讲解，而不是压缩术语清单。

推荐节奏：

1. **先读懂语法，再讲概念**：先拆代码怎么读，例如 `func f() (int, error)`、`v, ok := m[k]`、`type User struct`；再解释它对应的语言机制。
2. **先建立直觉，再给术语**：先说“只声明不赋值时，Go 自动给默认值”，再告诉读者这叫“零值”；避免一上来堆名词。
3. **用短例子验证效果**：抽象点尽量配一个能看见结果的例子，例如 `nil map` 能读不能写、切片共享底层数组、`%w` 才能被 `errors.Is` 识别。
4. **连接读者已知知识**：面向 JS 开发者时，可以类比 Node、Express、Promise、AbortController、对象解构等；类比时要说明“像什么”和“不像什么”。
5. **主动指出常见误解**：把容易误读的点提前挑明，例如“这不是解构赋值”“数组长度是类型的一部分”“JSON tag 不是字段名”“Go 编译器不会强制你检查 `err`”。
6. **最后收束到日常写法和面试表达**：读懂之后再讲工程里怎么写、面试怎么说。避免一开始就写成八股压缩包。

单个知识点可以使用这个微结构：

```markdown
### 主题

先读语法：这段代码每一部分是什么意思。

运行效果：给一个最小例子，展示输出或错误。

为什么这样：解释语言机制和设计取舍。

和已知知识的关系：对照 JS / Java / 浏览器 / Node 等已有经验。

常见坑：指出最容易写错的地方。

日常用法 / 面试要点：给最终可记忆的收束。
```

## 代码块

- 代码块必须标注语言，例如 ` ```ts `、` ```js `、` ```bash `。
- 代码块里的示例可以保留注释；正文不要用未围栏的代码片段冒充标题。
- 终端命令用 `bash`，配置文件按实际格式标注，例如 `json`、`ts`、`yaml`。

## 本地检查

提交前至少运行：

```bash
npm run check:content
npm run check:images
npm run docs:build
```

如果改了 Vue 笔记中的 HTML/Vue 示例，额外运行：

```bash
npm run check:vue:tags
```

完整 PR 自检运行：

```bash
npm run validate
```

`check:content` 目前会检查 `content/docs`、`docs`、`README.md` 和 `AGENTS.md`：

- 文章正文至少有标题，`content/docs/index.mdx` 除外。
- 同一篇文章最多一个 H1。
- H1 只能作为第一个标题出现。
- 第一个标题不能从 H3 或更深层级开始。
- 标题层级不能跳级。
- 标题中不能直接写 Markdown 链接。
- 相对 Markdown/MDX 路径不能只写在 inline code 里；需要跳转时必须使用 Markdown 链接。

`check:images` 目前会检查 `content/docs`：

- 本地图片引用必须使用 `./img/xxx` 形式。
- 本地图片引用的文件必须存在。
- 本地 Markdown 图片必须填写 alt 文案。
- 图片文件名必须使用英文小写、数字和短横线。
